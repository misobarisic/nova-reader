# Development and packaging

Build infrastructure derives from Nova revision
`b69a1e5765ecc65ac3b00acdfe2f16e2f46a5dda`. `flake.lock` preserves
Nova's exact nixpkgs/Fenix pins. The flake exports development shells rather
than packages: `default`, `spelling`, and Linux-hosted `android` and `windows`.
Reader builds require no native video, torrent, casting or sync libraries.

Use `nix develop --command make check` for formatting, Clippy, workspace checks,
tests and packaging regressions. Cross checks are:

```sh
nix develop .#windows --command cargo check --locked --target x86_64-pc-windows-gnu
nix develop .#android --command cargo check --locked --target aarch64-linux-android --no-default-features --features android --lib
```

Copy `.cargo/local-kit.example.toml` to `.cargo/local-kit.toml` to use sibling
`../nova-kit` through `cargo dev`, `cargo dev-run`, `cargo dev-release` and
`cargo dev-release-run`. CI always uses the committed Git dependency pins.

## Android

The app uses `.ReaderActivity`, a thin framework NativeActivity subclass for
Android document import, and loads `libnova_reader.so`. `cargo-apk2` compiles
`android/java` into DEX; no Gradle project is needed. Its ID is `dev.misob.nova.reader`; the display
name is Nova Reader. Internet access is declared for source networking.
`cargo-apk2` is pinned to `32b91331ff2371f3f06505ea6ceea3743e423a1c`
with Nova's CLI dependency lock and just the read-only-library and uncompressed
native-library fixes. Nova's PiP, receiver and version migration patches are
unnecessary here.

Android version codes are independent of Nova: upstream epoch 1 followed by
one byte each for major, minor and patch. Thus 0.1.0 is 16777472. Public Android
releases require stable three-component numeric versions, each component at
most 255, in strictly increasing semver order. Prereleases and build metadata
are rejected for release tags rather than sharing an ambiguous version code.

Local builds use the intentionally public debug key in `android/keystore`:

```sh
nix develop .#android --command make android-build-release
```

Signing uses Nova's selected-profile precedence: the
`CARGO_APK_<PROFILE>_KEYSTORE` / `_PASSWORD` environment overrides take priority
over the matching Cargo metadata profile. The intentionally public debug key
remains available for personal sideload builds; store distribution requires a
private override. If `ANDROID_KEYSTORE_BASE64` and `ANDROID_KEYSTORE_PASSWORD`
repository secrets are configured, the workflow imports that same existing key
for every ABI build and the assembly job. Both must be supplied together.
No signing identity is replaced when these overrides are present.

The workflow follows Nova's three parallel `android-build` matrix jobs (ARM64,
ARMv7 and x86_64), followed by `android-package` assembly. Each uploads its
`nova_reader.apk` as a separate input. The packager merges all three
`--abi-apk ABI=PATH` inputs, requiring identical manifests, resources and shared
assets. The local `android-build-release-universal` Make target remains an
alternative. Make invokes cargo-apk2 directly, as Nova does; its CLI does not
support Cargo's `--locked` argument. It emits ARM64, ARMv7, x86_64 and universal
APKs. The required Reader library is checked against its ABI, using Nova's
native payload validation. Root `build.rs` emits the 16 KiB page-size argument
on the final Android cdylib link: cargo-apk2 sets `CARGO_ENCODED_RUSTFLAGS`,
which overrides the target flags in `.cargo/config.toml`. Plain Cargo builds
still use those target flags. Per-ABI APKs store and align libraries to 16 KiB;
the universal APK compresses/extracts them. Every result is signed, signature
verified and compared with the original signing identity and payload.

## Desktop and distribution

Tagged builds use `cd-release`. Linux release binaries are built on Ubuntu
22.04 with system development libraries and packaged as Debian and AppImage
artifacts. The AppImage tools use dated release URLs and pinned SHA-256
checksums, as recorded below. Debian package
identity and dependency metadata are generated by Nova's Debian/AppImage
packaging flow. Windows builds use the Nix GNU cross toolchain. Its packager uses Nova's compiler-closure DLL staging with
`nix-store -qR`, preserves read-only Nix inputs and creates a flat ZIP. Windows
system libraries such as UIAutomationCore are supplied by Windows. The upload
uses `archive: false` and publication downloads that artifact by ID with
`skip-decompress: true`, preserving the original release ZIP.

The root `build.rs` copies Nova's actual `generate_license_catalog`,
`render_cargo_about` and `write_if_changed` functions from verified clean revision
`b69a1e5765ecc65ac3b00acdfe2f16e2f46a5dda`. `about.toml` and the crate-source
Handlebars template are byte-for-byte Nova copies; the license template changes
only the application header. Reader adaptations select its watched manifests,
actual desktop/Android/update-check features and local legal inputs. No Nova
media, unavailable font or brand-asset notices are added.

For the current Cargo target only, the builder performs the same two cargo-about
renders as Nova: source links and full license texts, both with `--locked --fail`.
Reader explicitly disables defaults and passes only the active features so an
Android or distro build does not acquire desktop/updater inventory. It appends
Reader's complete third-party notices, local AVIF adapter/vendor COPYING,
project GPL text and bundled Roboto Apache license. The compressed catalogue and
source rows are compiled into About, so no separate `target/licenses` output is
required by the Linux/Windows packagers. Android ABI jobs no longer generate
inventories for every other ABI before their own build.

Nova's compression code and recipe remain unchanged: zstd level 22, frame
checksum and pledged original size, with the original readable text, compressed
frame, exact-size Rust constant, source TSV and recipe in `OUT_DIR`. Identical
text plus the same recipe reuses the compressed frame on build-script reruns;
the two cargo-about renders still occur when the script runs. Missing tools,
unresolved licenses and invalid tool output fail the build rather than silently
omitting text. Nix shells still provide cargo-about; Linux CI retains its pinned
cargo-about installation. The old independent inventory script and its duplicate
policy/template are removed.

The workflow is copied from Nova with reader-specific names, paths and native
dependencies. Its job conditions and dependencies match Nova exactly: Linux,
Windows and Android check jobs run on pull requests and pushes to main, while
tag pushes start the three Android ABI builds, Linux build and Windows build
directly. Tag builds do not run or depend on check jobs. Android assembly waits
for its ABI builds; publication waits for Android assembly, Linux and Windows.
The existing Reader signing override and pinned cargo-about installation are
retained. License generation now runs inside the actual build, as Nova does.
Nova's pinned Actions, caches, disk cleanup, artifact transport and permissions
are unchanged. Tag names select the release version; version 0.1.2 carries this
correction without moving previously pushed tags.

The initial commit's Linux, Windows and Android checks passed in GitHub Actions.
The v0.1.0 packaging run exposed an unsupported cargo-apk2 flag and the custom
Windows DLL checker rejecting an OS library. Linux packaging also completed
both artifacts but failed its added Debian listing check because `grep -q`
closed the pipe early. Version 0.1.1 restores Nova's build/DLL staging paths and
consumes the complete Debian listing, with regressions covering all three failures. A complete artifact and device
smoke run is required before claiming installation and launch acceptance. Device launch, Android touch behavior and Windows execution
cannot be established by host-side archive and compile checks alone.

The Android shell includes host libclang with target-specific NDK sysroots for
QuickJS bindgen, plus GN/Ninja/Git/Curl for ARMv7 Skia source builds.
`make check-android-java` compiles the SAF activity against API 35; Android CI
runs it alongside the ARM64 Rust check with update checking enabled.

Version 0.1.5 compiled all three Android inputs but assembly rejected the ARM64
Reader library's 4 KiB ELF load-segment alignment. The same configuration remained
in versions 0.1.6 and 0.1.7. Version 0.1.8 sets alignment on the final cdylib link
instead of relying on the overridden Cargo flags. The regression links real ELF
libraries under encoded rustflags, reproduces the rejection without the Android
build directive, and verifies that the directive fixes it. This host-link test
does not replace the full Android build/sign/assembly run or device acceptance.

Version 0.1.9 re-copies the three platform packagers from Nova's immutable
baseline. Reader-only release gates (ELF segment inspection, video-library
rejection, extra Linux ldd/contents/extraction checks and a replacement Windows
bundle assertion) are removed. Nova's own merge, payload, ABI, ZIP alignment,
manifest, signing and artifact checks remain. The Android alignment build fix
from 0.1.8 remains, and its real-ELF regression is a development test only.
Make's build recipes now follow Nova directly, without the added preflight fetch.

Only Reader IDs/artifact names, its independent Android version-code policy,
omission of absent media libraries, Reader signing integration and the dated
AppImage tool resource pins below differ. Dependency notices are embedded by
Nova's copied build-time catalogue instead of separate package-copy steps. `test_package_nova_parity.py` compares all three packagers
with canonical digests derived from Nova b69a1e5, ignoring only these documented
app-specific adaptations and the exact reviewed tool URL/hash/comment literals;
adding a Reader-only release check still changes the digest. The separate Linux
tool regression asserts the new pins and fail-closed checksum behavior.
The workflow YAML's conditions, dependencies, commands and artifact transport
continue to follow Nova, with existing Reader license/signing integration.


## AppImage tool resource pins

The v0.1.14 Linux job stopped at checksum verification after the upstream
`continuous` linuxdeploy asset changed. The packager now selects these dated
releases; the download, checksum verification, execution and packaging flow
otherwise remain Nova's original implementation.

| linuxdeploy x86_64 | `1-alpha-20251107-1` | `cc7b86472c3caa3fd729b9dc502fd2aa78394257` | `313839329` | `c20cd71e3a4e3b80c3483cef793cda3f4e990aca14014d23c544ca3ce1270b4d` |
| linuxdeploy-plugin-appimage x86_64 | `1-alpha-20250213-1` | `a96502d15ce19ec1df3d46e6cbe87ddf38589a71` | `228937581` | `992d502a248e14ab185448ddf6f6e7d25558cb84d4623c354c3af350c25fccb3` |

Verification on 2026-11-01 downloaded each binary from its dated release URL.
The linuxdeploy bytes matched GitHub's independently reported release-asset
`digest` (`sha256:c20cd…`). The plugin's older release predates populated GitHub
asset digests: the API reports `digest: null`. Its SHA-256 was independently
confirmed by downloading asset ID `228937581` through the GitHub API with
`Accept: application/octet-stream` and comparing those bytes with the dated-URL
download. This is a second delivery-path check, not a publisher-provided digest
or signature. Both AppImages ran without FUSE using
`APPIMAGE_EXTRACT_AND_RUN=1`: linuxdeploy reported commit `cc7b864` and the plugin
reported plugin API version `0`.

GitHub reports `immutable: false` for both releases. The dated URLs prevent
future `continuous` updates from changing the selected tools; checked hashes
still reject any replacement of a dated asset. This does not claim that GitHub
has enabled immutable-release enforcement for these upstream repositories.

`test_package_linux.py` asserts both exact URL/hash/output-name tuples and
exercises the production download helper with matching and mismatching bytes.
The Nova parity test normalizes only those two URL/hash pairs and the explanatory
comment, preserving its immutable Nova script digest for the rest of the flow.
Neither test downloads mutable upstream tools during CI.

## Portable AVIF decoder on stable ARMv7

Version 0.1.14's 32-bit ARM build failed with E0554: the decoder requested
nightly ARM feature detection even though Reader disables its assembly feature.
The published `ferri-pdf-rav1d` 1.1.2 source is retained under `vendor/`, with
only its ARM/RISC-V nightly-feature predicates gated by `feature = "asm"`.
The existing scalar implementation and malformed-input fixes are unchanged.
The root Cargo patch selects this source; workspace exclusion keeps upstream
tests and defaults outside Reader's workspace. Full source/archive provenance,
licenses and the exact adjustment are in the vendor's `PATCHES.md`.

This codec-only cross-check reproduces the relevant ARMv7 feature selection
without needing the Android NDK:

```sh
rustup target add armv7-linux-androideabi
cargo check --locked -p ferri-pdf-rav1d -p ravif --target armv7-linux-androideabi
```

Full application APK builds still use Nova's existing three-ABI NDK workflow.
No nightly compiler, `RUSTC_BOOTSTRAP`, AVIF removal or tag-check job was added.


`test_package_license_build.py` pins canonical function/resource digests from
Nova's immutable source revision, normalizing only Reader-specific watched
inputs, active-feature selection, legal inputs and display header.
`tests/license_catalog_build.rs` invokes the actual copied generator in child
processes with mock cargo-about output. It checks current-target-only renders,
precise feature arguments, full local notice retention, exact zstd roundtrip,
checksum/content size, unchanged-frame reuse and recipe invalidation. Missing
tools, unresolved licenses and invalid UTF-8 must fail while preserving any
previous generated catalogue. The Android real-ELF alignment regression isolates
the unchanged final-link directive from this separately exercised license code.
